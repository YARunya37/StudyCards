# Development Guide

Документ описывает правила разработки проекта.

---

# Git Flow

Используется упрощённый Git Flow.

Основные ветки:

* `main` — стабильные версии проекта.
* `develop` — основная ветка разработки.

Рабочие ветки:

* `feature/<name>` — разработка новой функциональности.
* `fix/<name>` — исправление ошибок.

Все изменения выполняются только через отдельные рабочие ветки.

---

# Разработка новой функциональности

Пример разработки новой возможности.

## 1. Обновить локальный develop

```bash
git checkout develop
git pull
```

## 2. Создать новую ветку

```bash
git checkout -b feature/question-generator
```

## 3. Реализовать функциональность

Во время разработки рекомендуется делать небольшие логически завершённые коммиты.

---

## 4. Обновить ветку при необходимости

```bash
git checkout develop
git pull

git checkout feature/question-generator
git merge develop
```

---

## 5. Создать Pull Request

После завершения разработки создаётся Pull Request в ветку `develop`.

После прохождения проверки(*хотя бы одним человеком*) изменения объединяются в `develop`.

---

# Правила работы

## Общие правила

* **запрещено** выполнять прямые коммиты в `main`;
* **запрещено** выполнять прямые коммиты в `develop`;
* каждая задача выполняется в отдельной рабочей ветке;
* одна ветка — одна задача. Eсли задача сложная и требует реаилзации дополнительного функционала(модуля), то создаём новую ветку на основе ветки текущей задачи, либо добавляем на доску задач;
* после завершения работы рабочая ветка удаляется.

---

# Правила именования веток

Новая функциональность

```
feature/question-generator
feature/html-import
feature/note-editor
```

Исправление ошибок

```
fix/editor-crash
fix/html-parser
```

Используйте короткие и понятные названия на английском языке.

---

# Оформление Commit(стандарт Conventional Commits)

Каждый commit должен описывать одно логическое изменение.

Используются следующие префиксы:

```
feat:
fix:
refactor:
docs:
style:
test:
chore:
```

Примеры:

```
feat: add html export

fix: prevent crash while opening notes

refactor: simplify note repository

docs: update architecture documentation
```

---

# Pull Request

Каждая задача оформляется отдельным Pull Request.

Pull Request должен содержать:

## Название

Краткое описание реализованной функциональности.

Например:

```
Add HTML export
```

---

## Описание

В описании необходимо указать:

### Что сделано

* реализована возможность экспорта конспектов;
* добавлена обработка ошибок;
* обновлён пользовательский интерфейс.

### Что затронуто

* Core
* UI
* Документация(если таковая в проете будет добавлена)

### Архитектурные решения

Если в рамках задачи были приняты архитектурные решения или использовался какой-либо нестандартный инструмент Qt/c++, необходимо кратко объяснить их причину и последствия. 

Если архитектурных изменений нет — раздел можно не добавлять.

---

# Слияние Pull Request

Для объединения Pull Request используется режим **Squash and Merge**.

Это позволяет:

* сохранить чистую историю проекта;
* объединить промежуточные коммиты разработки;
* оставить одно осмысленное изменение в истории Git.

После успешного объединения рабочая ветка должна быть удалена.

# Architecture

Документ описывает архитектуру проекта и основные инженерные принципы, используемые при разработке.

---

# Архитектурные цели

Архитектура проекта строится вокруг следующих целей:

* разделение ответственности;
* минимальная связанность модулей;
* высокая читаемость кода;
* простота сопровождения;
* возможность постепенного расширения функциональности.

При разработке новые компоненты должны органично встраиваться в существующую архитектуру без необходимости изменения уже работающих модулей.

---

# Общая архитектура

Проект разделён на два основных модуля.

```text
+----------------------+
|         UI           |
+----------------------+
           │
           ▼
+----------------------+
|        Core          |
+----------------------+
           │
           ▼
+----------------------+
| Storage / Filesystem |
+----------------------+
```

---

# UI

Модуль пользовательского интерфейса.

Отвечает исключительно за взаимодействие с пользователем.

Основные обязанности:

* отображение информации;
* обработка действий пользователя;
* отображение результатов работы Core;
* навигация между окнами приложения.

UI **не содержит бизнес-логики**.

Допускается только преобразование пользовательских действий в вызовы Core.

---

# Core

Core содержит всю бизнес-логику проекта.

Отвечает за:

* обработку данных;
* управление документами;
* генерацию билетов;
* работу с конспектами;
* импорт и экспорт документов;
* внутренние алгоритмы приложения.

Core не должен зависеть от пользовательского интерфейса.

Любая возможность приложения должна оставаться работоспособной даже при замене интерфейса.

---

# Хранение данных

На текущий момент данные сохраняются в локальных HTML-документах. Обусловленно форматом виджетов Qt - html самый совместимый и удобный вариант.

Для поддержки различных форматов используется Pandoc.

Работа с файловой системой должна быть сосредоточена в Core и не должна выполняться непосредственно из UI.

Файлы связанные с действиями пользователей находятся в /resources/... 

---

# Направление зависимостей

Допустимые зависимости:

```text
UI
    ↓
Core
    ↓
Storage
```

Недопустимые зависимости:

```text
Core → UI

Storage → UI
```

Core не должен знать о существовании пользовательского интерфейса.

---

# Основные принципы

## Single Responsibility Principle (SRP)

Каждый класс должен иметь одну ответственность.

Например:

* генератор билетов не должен сохранять файлы;
* редактор заметок не должен выполнять импорт документов.

---

## Open/Closed Principle (OCP)

Новые возможности должны добавляться посредством расширения существующих компонентов, а не изменения уже работающего кода. Иногда это придется нарушать, что в PR **обязательно** нужно указывать

---

## DRY

Не допускается дублирование бизнес-логики.

Общий код необходимо выносить в отдельные классы или функции. Уже наступали на эти грабли, возможно пойдет на исправление

---

## KISS

Предпочтение отдаётся простым решениям.

Не следует проектировать сложные абстракции без реальной необходимости.

---

## YAGNI

Не реализовывать функциональность "на будущее".

Добавление новых компонентов должно происходить только при появлении реальной потребности.

---

# Dependency Injection

На текущем этапе **Dependency Injection в проекте не используется**.

Причины:

* команда ещё не использует DI осознанно;
* отсутствует практический опыт применения;


Взаимодействие между компонентами осуществляется через явную передачу зависимостей и композицию объектов.

---

# Масштабирование проекта

При добавлении нового функционала рекомендуется придерживаться следующих правил:

* не нарушать существующее разделение ответственности;
* не переносить бизнес-логику в UI;
* минимизировать зависимости между компонентами;

Соблюдение этих принципов позволит сохранить проект понятным, поддерживаемым и готовым к дальнейшему развитию.
